  'ampliata automaticamente quando serve.
  'context non e' un'entita' distinta: e' il dataset selezionato dal ciclo
  'in durante l'iterazione corrente.


  taskdecl= task name([varname {,varname} ])  "{" [codice] "}"

  targetdecl= target name([varname {,varname} ])  "{" [codice] "}"

  'task parametri, stato e meccanismo di esecuzione, ma non il significato.
  'i parametri del target sono passati per valore, come nelle funzioni.

  vardecl= var singlevar [, singlevar]

  ifblock= if calcexp blocco [elseif calcexp blocco] { else blocco } 
  forblock= for (calcexp; calcexp; calcexp) { [codice] }

  
  whileblock= while calcexp { [codice] };
  downwhile= do { [codice] } while calcexp;
  foreachblock= foreach (variabile,calcexp) { [codice] }
              | foreach (chiave,variabile,calcexp) { [codice] }
  'scorre dal primo all'ultimo senza copiare l'intero array; con una variabile
  'espone il valore, con due espone chiave e valore.
  'visita sia chiavi numeriche sia associative, nell'ordine della struttura.
  'modificare durante il ciclo la stessa struttura attraversata ha
  'comportamento indefinito.
  fundecl= sub name([varname {,varname} ]) [ { [codice] } ]

  calcexp= assign\= inexp | inexp         //    (no ll1 ! attento) 
  assign=variabile  [ "[" pos "]" ]     //Notare che ci sono gli array multidimensionali
  inexp=exp  cfr inexp | exp
  cfr = == | != | <= | >= | > | < | eq | neq | gt | ge | lt | le
  'gli operatori simbolici confrontano numeri e fanno raise se uno degli
  'operandi non e' interamente numerico; quelli alfabetici confrontano testo
  'byte per byte.
  'eq e neq possono confrontare due array marcati in forma canonica; l'ordine
  'fa parte della struttura. Confronti misti e lt/le/gt/ge sugli array raise.
  exp=e . exp | e
  e = t+e | t-e | t
  t = f*t | f/t | f%t | f
  'divisione e resto per zero provocano raise.
  '% applica prima int() ai due operandi; le frazioni sono troncate verso zero.
  f= b\|f | b\|\|f | b
  b= k & b | k && b | k
  '| e & conservano la semantica bitwise intera della VM; || e && usano la
  'verita' EWB.
  '|| e && valutano sempre entrambi gli operandi, da sinistra a destra.
  k= variabile [ "[" calcexp "]" ] | ! inexp | numvalue | strvalue | (calcexp) | identifier 
  identifier = variabile | funzione
  funzione = predef | fname "(" [calcexp {,calcexp}] ")"
  'le parentesi sono obbligatorie per tutte le chiamate di funzione,
  'comprese le funzioni predefinite.
'qui mi complico la vita, ma almeno posso definire i numeri in qualunque base e dimensione.. 
  numvalue = [+/-] ( bin | hex | oct | dec ) 
  bin = 0b [0..1] [. {0..1} ]
  oct = 0o [0..7] [. {0..7} ]
  hex = 0x ([0..1]|[A..F]|[a..f])  [. {([0..1]|[A..F]|[a..f])} ]
  dec = [0..9] [. {0..9} ]
  'la parte frazionaria e' ammessa in tutte le basi, non soltanto in decimale.
  'la notazione esponenziale non fa ancora parte della sintassi.
  strvalue = \" carattere \"
  variable =a..z|A..Z | _  [a..z | A..Z | 1..9 | _ ] 
  fname =variabile
  'operatori e funzioni numeriche accettano soltanto stringhe interamente
  'conformi a numvalue; una conversione parziale provoca raise.
  'sono falsi la stringa vuota e ogni numvalue uguale a zero; ogni altra
  'stringa non vuota e' vera.
  'un array marcato e' falso se non contiene chiavi, vero altrimenti.
  'operatori logici e confronti restituiscono sempre "0" oppure "1".

  'una struttura inizia con il byte ASCII 0x1E. Seguono eventualmente elementi
  'hex(chiave):hex(valore), separati da un solo spazio. Non collassa:
  '"30:3138" e' uno scalare; 0x1E+"30:3138" e' [0]="18".

  'il runtime produce chiavi uniche; sostituire un valore non sposta la

  'interamente canonico; una struttura marcata malformata provoca raise.

  'e' accettato come caso neutro; un'operazione mutante lo promuove ad array
  'aggiungendo il marcatore.

  'provocano raise. Le operazioni opache di I/O, come save, restano ammesse.

  'lock e unlock restituiscono "1" in caso di successo.
  'lock apre una transazione sulla risorsa. Un secondo lock sulla stessa
  'risorsa nello stesso flusso provoca raise. Senza unlock, dopo 30 secondi
  'la transazione scade e provoca raise. Unlock esegue commit.
  'ogni raise esegue automaticamente il rollback di tutte le transazioni
  'ancora aperte prima di entrare nell'handler; un retry riparte da capo.
  'ask/showform non possono sospendere con transazioni aperte: STOP esegue
  'prima il rollback e poi raise. Senza transazioni, sospende normalmente.
  'anche la fine normale con transazioni aperte esegue rollback e raise:
  'ogni lock deve essere chiuso da un unlock esplicito.
  'sono ammessi lock contemporanei su database differenti. Dataset che
  'risolvono allo stesso motore/database identificano la stessa risorsa.
  'non c'e' ancora commit atomico fra database: ogni unlock conferma subito
  'la propria risorsa e la sequenza puo' fallire lasciando commit parziali.
  inblock = in ( variabile[.variabile] [, condizione] ) blocco | delete ( variabile[.variabile] [, condizione] )

  '_orderby contiene un frammento SQL libero. Se vale "nome, cognome>2",

  'criterio. Se _orderby e' vuoto, l'ordinamento e' soltanto per id.

Per uso di minmax e euristiche ? 

Formato base, vicino al vecchio motore:

  dataset pianificazione = 
  { [ nomeregola/nomefatto {= regola} ] 
    fatto(...),
    fatto(...),
    regola(...) :- condizioni(...)
  }
  
  Estensione euristica minima:

  goal pianificazione, soluzione max score {
    ...
  }

  Dove score può essere:

  - una variabile prodotta dalla regola;
  - una funzione;
  - una calcexp valutata sulle variabili del goal.

  Esempio più semplice:

  dataset assegnazioni = {
    tecnico("Marco","VR","radio",3),
    tecnico("Luca","VI","radio",1),
    tecnico("Anna","VR","radio",2),

    adatto(Nome,Zona,Skill,Carico) :-
      tecnico(Nome,Zona,Skill,Carico),
      Zona == "VR",
      Skill == "radio"
  }

  goal assegnazioni, adatto(Nome,Zona,Skill,Carico) min Carico {
    print Nome
  }

Ipotesi:
Task e Target sono la stessa cosa.

Problema:
Si confondono esecuzione e presentazione.

Decisione:
Il Target estende il Task, ma i due concetti restano distinti.

Io la vedrei quasi così (in termini OO, anche se poi la VM non sarà OO):

              Executable
                  │
        ┌─────────┴─────────┐
        │                   │
      Task              Target

Dove Executable definisce:

contesto
parametri
stato
trigger
logging
timeout
lock
gestione errori

Il Task aggiunge:

cron
unique
ready/error
result

Il Target aggiunge:

renderer
id/class
ajax
refresh
eventi UI

Quindi il runtime vede sempre un oggetto eseguibile.

Per esempio.

task generaStatistiche
{
    ...
}

e

target statistiche ajax every "30s"
{
    ...
}

internamente sono quasi identici.

Il secondo diventa:

Task
    |
    +-- Renderer HTML
    +-- Trigger AJAX
    +-- Target ID

Questo porta ad una conseguenza interessante.

Un target potrebbe essere lanciato anche senza browser.

Ad esempio:

render(statistiche,"pdf");

oppure

render(statistiche,"json");

Perché il target non è HTML.

È una funzione che produce una vista.

HTML è solo uno dei renderer.

Ed ecco una cosa che mi è venuta in mente adesso.

Se i target sono "task con renderer", allora potrebbero avere cache.

target dashboard
cache 30s
{
    ...
}

Il runtime dice:

"L'ho già calcolato 12 secondi fa."

e restituisce direttamente il rendering.

Oppure:

target mappa
invalidate on comuni
{
    ...
}
